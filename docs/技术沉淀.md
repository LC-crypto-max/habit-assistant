# 技术沉淀：多用户兴趣画像与推荐平台

## 1. 阶段目标

项目从本地个人助手升级为小规模在线协作平台。多个用户可以在同一个 URL 提交数据，系统按用户沉淀画像并生成推荐。

## 2. 核心链路

```text
浏览器 / PowerShell / 微信小程序 / 飞书机器人
  -> REST Controller
  -> Service 业务层
  -> Repository
  -> H2 或 MySQL
```

## 3. 多用户隔离

当前使用 `userId` 作为轻量身份标识。行为、画像、推荐都存储 `userId`：

- `UserActivity.userId`
- `InterestTerm.userId`
- `Recommendation.userId`

正式上线后，应增加登录鉴权，由服务端从登录态解析用户，而不是长期信任前端传入的 `userId`。

## 4. 画像和推荐

行为进入 `ActivityService` 后会抽取关键词并更新兴趣词权重。`RecommendationService` 读取兴趣词，调用多个 collector 获取候选内容，再按命中兴趣词、发布时间、搜索关键词和显式反馈等规则打分。

已有 collector：

- Mock 内容源
- 用户访问记录内容源
- RSS/Atom
- 配置化 JSON API
- X Recent Search

小红书接入采用分阶段策略：

- MVP：用户主动提交小红书链接、搜索词或 CSV，统一使用 `platform=xiaohongshu`。
- 小程序/飞书：作为用户授权后的提交入口，复用 `/api/mini/**`、`/api/visits`、`/api/activities`。
- 授权数据源：后续拿到官方或授权 API 后，新增 `XiaohongshuAuthorizedCollector`，输出统一的 `CollectedContent`。

详细方案见 `docs/xiaohongshu-integration-plan.md`。

### 4.1 推荐排序升级

当前推荐分数由几类信号组成：

- 画像兴趣词：标题命中权重最高，摘要命中次之，标签命中再次之。
- 临时搜索词：`POST /api/recommendations/search` 会把关键词记录为搜索行为，并在本次推荐中提高相关内容分数。
- 新鲜度：6 小时、24 小时、7 天内内容分别获得不同加分。
- 显式反馈：`LIKE`、`FAVORITE`、`READ` 提升相似平台和标签；`DISLIKE` 降低相似内容；`BLOCK_SOURCE` 过滤同平台候选。

反馈更新后，系统会额外写入一条用户行为，让画像层继续学习。这样下一次推荐既看长期兴趣，也看用户刚刚表达的喜好和厌恶。

### 4.2 本地采集边界

浏览器历史和本机应用检测属于高敏感数据，当前采用显式脚本触发，不做静默后台读取：

- `scripts/import-browser-history.ps1`：复制 Chrome/Edge 历史 SQLite 文件，读取最近 URL 并写入 `/api/visits`。
- `scripts/collect-app-usage.ps1`：检测指定进程或窗口标题，例如哔哩哔哩客户端，命中后写入 `/api/activities`。
- 小红书数据不做模拟登录抓取，优先通过用户主动提交链接、CSV、小程序或飞书机器人采集。

这一设计方便本地验证，也保留了上线时的合规边界：多用户协作场景下应由用户主动上传数据，或通过清晰授权后的客户端采集。

## 5. 推荐刷新

默认策略：

```text
自动读取：12 小时过期后自动刷新
手动点击：调用强制刷新接口，立即重新生成
```

配置项：

```yaml
assistant:
  recommendation-refresh:
    activity-window-hours: 24
    medium-activity-threshold: 20
    high-activity-threshold: 80
    low-activity-hours: 12
    medium-activity-hours: 12
    high-activity-hours: 12
```

接口：

- `GET /api/recommendations/today`：返回今日推荐；如果推荐不存在或超过 12 小时则自动刷新。
- `POST /api/recommendations/refresh`：强制刷新推荐，前端手动刷新按钮使用该接口。
- `GET /api/recommendations/refresh-policy`：查看当前用户推荐的过期时间和近 24 小时行为量。

## 6. 在线协作部署

推荐第一版线上架构：

```text
Nginx + HTTPS
  -> Spring Boot Jar
  -> MySQL
```

MySQL 是线上数据底座，用于保存用户行为、画像、推荐和反馈。H2 只保留本地开发使用。

上线建议：

- 使用 HTTPS 域名。
- 开启 MySQL 定时备份。
- 使用环境变量管理数据库密码和飞书 webhook。
- 为接口增加登录鉴权和简单限流。
- 小程序上线时使用微信登录态绑定内部用户。

### 6.1 H2 与 MySQL 查询方式

项目当前支持两种数据库运行方式：

- H2：默认本地开发库，配置在 `application.yml`，数据文件为 `./data/assistantdb`。
- MySQL：协作和长期运行建议使用，配置在 `application-dev.yml` 或 `application-mysql.yml`。

核心落库表：

- `user_activity`：用户行为和 worker 回调后的访问记录。
- `interest_term`：画像关键词、权重、命中次数和最近出现时间。
- `recommendation`：每日推荐结果、分数、原因和反馈状态。
- `content_item`：推荐内容池，包含平台、标题、链接、摘要和来源信息。

优先用 API 查询，因为它同时适用于 H2 和 MySQL：

```powershell
Invoke-RestMethod "http://localhost:8080/api/profile?userId=me" | ConvertTo-Json -Depth 6
Invoke-RestMethod "http://localhost:8080/api/activities/recent?userId=me" | ConvertTo-Json -Depth 6
Invoke-RestMethod "http://localhost:8080/api/recommendations/today?userId=me" | ConvertTo-Json -Depth 6
```

MySQL 直连查询：

```sql
select id, user_id, platform, type, title, url, occurred_at
from user_activity
where user_id = 'me'
order by occurred_at desc
limit 20;

select term, weight, hit_count, last_seen_at
from interest_term
where user_id = 'me'
order by weight desc
limit 20;

select r.id, r.recommendation_date, r.score, r.reason, c.platform, c.title, c.url
from recommendation r
left join content_item c on c.id = r.content_item_id
where r.user_id = 'me'
order by r.created_at desc
limit 20;
```

H2 查询方式：

```text
http://localhost:8080/h2-console
JDBC URL: jdbc:h2:file:./data/assistantdb;FILE_LOCK=NO
User Name: sa
Password: 留空
```

H2 Console 中可执行与 MySQL 类似的 SQL。如果表名大小写不匹配，可使用大写表名，例如 `USER_ACTIVITY`、`INTEREST_TERM`。

本轮本地验证结果：

- 后台启动 jar 后 `/actuator/health` 返回 `UP`。
- `GET /api/profile?userId=me` 已返回画像关键词，例如 `agent-reach`、`agent-task`、`local app` 等。
- `GET /api/activities/recent?userId=me` 已返回最近 worker 写入的访问记录，包括 `web`、`xiaohongshu`、`local-terminal` 等平台。
- `GET /api/recommendations/today?userId=me` 已返回推荐列表，说明兴趣内容、画像和推荐数据已经保存并可被后端读取。

## Python 本地代理：应用信息采集边界

新增脚本：

```text
scripts/codex_app_proxy.py
```

它不是调用 Codex 内部隐私接口，而是在用户显式运行时作为本地 Agent 代理：

```text
本地可见应用窗口
  -> Python 代理采集进程名和窗口标题
  -> 转换为 BehaviorEvent
  -> POST /api/v1/behavior-events/batch
  -> MySQL/H2
  -> Profile / Recommendation
```

运行模式：

- `--dry-run`：只输出采集结果，不上传。
- `--once`：采集一次并上传。
- `--serve`：启动 `127.0.0.1:8765` 本地 HTTP 代理。

合规边界：

- 只采集当前有窗口标题的应用，不读取应用内部文件、聊天内容或账号数据。
- 用户必须主动运行脚本或主动调用本地代理。
- 如需更深入的浏览器/应用行为，应使用浏览器插件、官方授权 API、用户导出文件或明确授权的本地客户端。

## Codex / Agent Reach 代理数据回调架构

本轮新增了面向 Codex CLI、Agent Reach、本地脚本和 Skill 的统一任务回调入口：

```text
任务 JSON
  -> Codex Agent / Codex CLI
  -> 本地脚本或 Skill
  -> 数据源适配器
  -> 非隐私兴趣数据
  -> POST /api/agent/tasks
  -> BehaviorEventService
  -> Activity / Profile / Recommendation
```

落地文件：

- `src/main/java/com/example/assistant/controller/AgentTaskController.java`
- `src/main/java/com/example/assistant/service/agent/AgentTaskService.java`
- `src/main/java/com/example/assistant/dto/AgentTaskRequest.java`
- `src/main/java/com/example/assistant/dto/AgentInterestItemRequest.java`
- `src/main/java/com/example/assistant/dto/AgentTaskResponse.java`
- `docs/agent-task-architecture.md`

### 当前已经具备的能力

- 可以从前端后台粘贴 Codex / Agent Reach 返回的结构化 JSON。
- 可以通过脚本直接调用 `POST /api/agent/tasks`。
- 可以兼容小红书、Bilibili、YouTube、微信公众号、普通网页等平台字段。
- 可以设置 `ingest=false` 只做预览，不写入数据库。
- 可以设置 `ingest=true` 写入行为事件，触发画像更新，然后刷新推荐。
- 可以通过 `GET /api/recommendations/today?userId=alice` 返回用户可能感兴趣的内容。

### 当前不能误解的边界

项目目前还不是“Java 后端主动驱动 Codex 查询”的架构。准确说：

```text
已支持：Codex / Agent Reach -> 结构化 JSON -> Java 后端 -> 推荐结果
未支持：Java 后端 -> 自动启动 Codex CLI -> 等待 Codex 抓取 -> 自动回写
```

这个边界是刻意保留的，原因有三点：

- Codex / Agent Reach 的执行通常依赖本机权限、登录态、代理和用户确认。
- 后端不应该静默读取用户账号、cookie、浏览历史或平台私域数据。
- 先把“回调协议”和“推荐闭环”固定下来，后续再把主动代理查询做成可开关、可审计的本地 worker。

### 终端调用 Codex 查询应用访问记录

当前可以在终端上配合 Codex / Agent Reach / 本地脚本完成“授权式应用访问记录采集”，但它必须遵守 Codex Data Agent 的安全边界。

推荐链路：

```text
用户先调用 /api/user-data-authorization/grant 完成授权
  -> 终端运行本地脚本、Agent Reach 或 Codex worker
  -> worker 只读取授权范围内的非敏感访问行为
  -> worker 输出结构化 JSON
  -> 回调 /api/codex-agent/daily、/api/codex-agent/client/app-usage 或 /api/agent/tasks
  -> Spring Boot 生成 InterestEvent、DailyProfile、DailyRecommendation
```

当前可以处理：

- App 使用概况：App 名称、包名、使用时长、打开次数。
- 浏览器历史：URL、标题、访问时间、访问次数。
- 本地授权目录：Markdown、文本、CSV、JSON、HTML 笔记或收藏链接。
- 公开网页元信息：`title`、`description`、`keywords`。

当前不能处理：

- App 内部页面内容、微信聊天记录、私信、通讯录、支付记录。
- Cookie、Token、Session、Authorization Header、账号密码、验证码。
- 平台私有接口或受保护内容的批量抓取。

因此，“终端调用 Codex 查询应用访问记录”在本项目中的准确含义是：终端侧 Agent/worker 读取用户授权范围内的非敏感摘要，再把结构化结果交给后端。它不是让 Java 服务静默控制 Codex 进入各 App 或网站账号内部读取数据。

### 平台适配策略

小红书：

- 优先接收用户主动提交的公开笔记链接、摘要、标签和收藏意图。
- 不做模拟登录抓取，不提交 cookie、私信、账号隐私字段。
- Agent Reach 读取到的公开笔记可映射为 `platform=xiaohongshu`、`type=FAVORITE` 或 `VISIT`。

Bilibili：

- 视频链接、标题、UP 主、AI 总结、字幕摘要可以映射为 `platform=bilibili`。
- 用户看过或让 Agent 读取过的视频通常用 `type=WATCH`。
- BV 号放入 `externalId`，便于后续去重。

YouTube：

- 视频标题、频道、字幕摘要、标签可映射为 `platform=youtube`。
- `externalId` 使用 video id。
- 如果只是搜索候选内容，可用 `type=SEARCH` 或 `VISIT`。

### 前端回调面板

`src/main/resources/static/index.html` 已重做为干净 UTF-8 页面，并新增“Codex 自动查询工作台”。页面把 Agent/Codex 流程拆成两步：

```text
申请 Codex 自动查询
  -> POST /api/agent/queries
  -> 后端创建任务和 prompt
  -> 本地 worker / Codex 领取并执行
提交 Codex 返回结果
  -> POST /api/agent/tasks
  -> 后端写入兴趣事件并刷新推荐
```

界面支持的申请类型：

- 终端应用访问概况；
- 浏览器历史标题与 URL；
- 公开 URL 元信息；
- 授权目录本地笔记。

界面仍保留结构化回调区域：

- 支持平台选择：小红书、Bilibili、YouTube、微信公众号、网页。
- 支持填入示例、预览转换、提交并刷新。
- 支持单个 JSON 对象、数组，或 `{ "items": [...] }` 结构。
- 提交成功后自动强制刷新推荐列表。

安全边界：

- “申请自动查询”只创建任务，不代表 Spring Boot 已经读取用户设备。
- 真正读取动作必须由本地 worker/Codex 在用户授权范围内执行。
- 回传结果必须是公开或非敏感摘要，不允许包含 Cookie、Token、Session、聊天记录、私信、通讯录和支付记录。

### 当前自动查询执行状态

前端界面的“申请 Codex 自动查询”目前已经打通到后端任务创建，但还没有自动执行 worker。

实际链路是：

```text
前端点击“申请自动查询”
  -> POST /api/agent/queries
  -> AgentQueryService 创建 AgentQueryTask
  -> 状态为 PENDING，并生成 prompt

前端点击“领取待执行任务”
  -> POST /api/agent/queries/claim-next
  -> 任务状态变为 RUNNING
  -> 页面展示 taskId、platform、intent、prompt

用户或外部 worker 执行任务后
  -> POST /api/agent/queries/{taskId}/result
  -> 后端复用 /api/agent/tasks 写入兴趣事件
```

目前没有发生的事情：

- 没有常驻 Python 脚本自动轮询 `/api/agent/queries/claim-next`。
- 没有 CLI 自动启动 Codex。
- 没有自动调用 `agent-reach` skill。
- 没有从 App 内部读取真实页面、聊天、私信、Cookie、Token 或 Session。

已有脚本状态：

- `scripts/codex_app_proxy.py` 可以采集 Windows 当前可见窗口/进程快照。
- 它会把结果转换成 `/api/v1/behavior-events/batch`。
- 它不消费 `AgentQueryTask` 队列，也不调用 Agent Reach。
- 它不能提供严格的“今日使用时长/打开次数”，只能提供当下可见窗口快照；真实使用时长仍需要 Android Usage Access 客户端或本地授权 worker 上报。

Agent Reach 的定位：

- Agent Reach 是 Codex 运行环境里的平台读取能力，适合搜索 B站、读取 B站/YouTube 字幕、读公开网页等。
- 它不是 Spring Boot 进程内的 Java Bean，也不会被前端按钮自动触发。
- 如果要自动使用 Agent Reach，应新增一个外部 worker，由用户显式启动，再由 worker 根据任务内容调用 `bili`、`yt-dlp`、`agent-reach` 或其他本地命令。

下一步可实现的 worker 形态：

```text
codex_query_worker.py
  -> claim-next
  -> 根据 adapter/platform/intent 路由：
       local-terminal/app-usage-summary：读取本地授权 App usage 摘要或客户端上报数据
       bilibili/read-video：调用 bili/yt-dlp/agent-reach
       youtube/read-video：调用 yt-dlp
       browser-history-summary：读取授权浏览器历史导出
       local-notes/read-note：读取 allowedPaths 下文件
  -> PrivacySanitizer 等价脱敏
  -> POST /api/agent/queries/{taskId}/result
```

这个 worker 应作为用户主动启动的本地进程，而不是后端静默后台任务。

### 下一阶段建议

如果要实现“项目主动从 Codex 处进行代理数据查询”，建议新增一个本地 worker，而不是让 Spring Boot 直接调用交互式 Codex。当前已经新增后端任务队列骨架：

```text
POST /api/agent/queries
  -> Spring Boot 创建 AgentQueryTask
  -> 本地 worker 轮询待处理任务
  -> worker 调用 agent-reach / Codex CLI / 平台脚本
  -> worker 清洗隐私字段
  -> worker 回调 POST /api/agent/queries/{taskId}/result
  -> Spring Boot 复用 POST /api/agent/tasks 做结构化入库
  -> Spring Boot 返回推荐
```

这样能保留用户确认、日志审计、失败重试和权限隔离，也更适合以后扩展到小红书、Bilibili、YouTube 多平台。

新增接口：

- `POST /api/agent/queries`：由 Java 后端创建待执行查询任务，生成给 Codex/Agent Reach 使用的 prompt。
- `POST /api/agent/queries/claim-next`：worker 领取最早的 `PENDING` 任务，状态变为 `RUNNING`。
- `GET /api/agent/queries/{taskId}`：查询任务状态。
- `POST /api/agent/queries/{taskId}/result`：worker 回传成功或失败结果；成功时可直接入库并更新画像。

困难和风险：

- Codex CLI 通常是交互式工具，可能需要用户确认权限、网络访问、文件访问和命令执行；不适合由线上 Spring Boot 静默启动。
- Agent Reach、Bilibili、YouTube、小红书等渠道的可用性依赖本机网络、代理、登录态、字幕/公开接口是否可用。
- 平台内容读取容易混入隐私字段，worker 必须做字段白名单，只回传公开标题、链接、作者、摘要和标签。
- 异步任务需要失败重试、超时回收和幂等去重；当前实现是最小闭环，后续应增加 worker token、任务租约和重复 URL/BV/videoId 去重。
- 后端发起查询会带来成本和速率限制，正式部署前需要限流、审计日志和用户级配额。

## Recommendation 模块：标签打分与反馈闭环

本轮新增页面友好的推荐接口：

```text
GET /api/v1/recommendations/today?userId=alice&refresh=false
```

推荐分数由几类信号组成：

- 兴趣标签命中标题：权重最高。
- 兴趣标签命中摘要：中等权重。
- 兴趣标签命中内容标签：基础权重。
- 临时搜索词命中：额外加权。
- 内容发布时间较新：新鲜度加权。
- 历史点击、喜欢、收藏：提升相似平台和标签。
- 历史不感兴趣、屏蔽来源：降低相似平台和标签，必要时过滤平台。

页面输出结构：

- `summary`：今日推荐自然语言摘要。
- `profileTags`：当前画像标签和权重。
- `items`：推荐卡片列表。
- `items[].matchedTags`：本条内容命中的画像标签。
- `items[].actions`：前端可直接绑定的点击、不感兴趣和通用反馈接口。

反馈闭环：

```text
POST /api/v1/recommendations/{id}/click
  -> feedback = READ
  -> 写入 VISIT 用户行为
  -> ProfileService.learnFrom 增强相关标签

POST /api/v1/recommendations/{id}/not-interested
  -> feedback = DISLIKE
  -> 写入 DISLIKE 用户行为
  -> ProfileService.learnFrom 降低相关标签权重
```

这样前端的每次点击和“不感兴趣”都会回流到画像层，下一轮 `refresh=true` 或推荐过期自动刷新时会体现变化。

### Worker 敏感信息策略修复

本轮修复了 `scripts/codex_query_worker.py` 的一个误拦截问题：前端或后端生成的任务 query 中如果写了“不读取 Cookie、Token、Session、账号信息”，旧实现会因为简单命中 `Cookie`、`Token`、`Session` 这些词而直接返回 `Task contains blocked sensitive keywords.`。

修复后的策略从“单纯关键词匹配”升级为“敏感对象 + 危险动作 + 否定上下文”：

- 敏感对象：Cookie、Token、Session、Authorization、账号密码、聊天记录、私信、验证码等。
- 危险动作：读取、获取、提取、导出、上传、返回、解密、read、get、extract、export、upload 等。
- 否定上下文：不读取、不获取、不上传、不包含、不携带、do not read、without reading、exclude 等。

判断原则：

- `不读取 Cookie/Token/Session/账号信息` 和 `do not read cookies/tokens` 是安全边界声明，允许通过。
- `读取 Cookie`、`获取 Token`、`导出 Session`、`读取聊天记录/私信/账号密码` 是明确敏感读取请求，必须拒绝。
- `token=xxx`、`cookie=xxx`、`authorization: bearer xxx` 这类疑似真实密钥值，无论上下文如何都直接拒绝。
- `不读取 Cookie，但获取 Token 并上传` 这种前后矛盾的混合表达仍然拒绝，避免被前半句的否定词绕过。

同时，后端 `AgentQueryService` 生成给 worker 的 prompt 已调整为“只返回公开元信息和隐私安全摘要”，前端 Codex 查询预设也改为“只返回公开页面元信息和访问摘要”，尽量避免在默认任务文案里出现高敏词。

测试覆盖：

```powershell
py -3 -B -m unittest scripts.test_codex_query_worker_policy
mvn test
```

当前覆盖用例包括：

- 中文否定表达放行。
- 英文否定表达放行。
- 明确读取 Cookie / 获取 Token / 导出 Session 拒绝。
- 聊天记录、私信、账号密码拒绝。
- 密钥值形态拒绝。
- 前后矛盾的混合表达拒绝。

为什么仍然不让后端直接启动 Codex：

- Codex CLI / Agent Reach 的运行通常依赖本机终端权限、网络、代理、登录态和用户确认。
- Spring Boot 作为服务端进程不应静默打开用户设备或平台账号数据。
- 用户授权必须落在实际执行边界上，所以 worker 在终端展示任务并逐次确认。
- `agent-reach` skill 是 Codex 环境能力，不是项目里的 Java Bean；后端只能创建任务和接收回调。

当前可以回答“前端提交自动查询后会发生什么”：

- 会创建后端 `AgentQueryTask`。
- 如果用户启动 `scripts/codex_query_worker.py`，worker 会领取任务、请求终端授权、执行安全采集并回调。
- 如果用户没有启动 worker，任务只会停留在 `PENDING`，不会自动查询。
- 若任务是 B站/YouTube 公开内容，worker 可调用 `yt-dlp` 或 `bili` 这类本地 CLI。
- 若任务是终端应用访问概况，worker 不使用 Agent Reach，只读取当前可见窗口快照；严格的每日使用时长/打开次数仍应走 Android Usage Access 上报或授权统计文件。

### 前端触发本地 Python worker 的可行性

浏览器安全模型不允许网页直接启动用户电脑上的 Python、PowerShell 或 Codex CLI。因此不能实现“纯前端页面直接执行脚本”。可行方案是在用户本机运行 Spring Boot 后端时，提供一个本地受限接口，由前端调用 localhost 后端，再由后端启动本地 worker。

本轮实现的接口：

```text
POST /api/agent/worker/start-once
```

执行链路：

```text
前端点击“启动本地 worker”
  -> POST /api/agent/worker/start-once
  -> LocalAgentWorkerService 检查配置开关和请求来源
  -> Windows 上打开可见 PowerShell 窗口
  -> py -3 scripts/codex_query_worker.py --once --base-url http://localhost:8080
  -> worker 展示任务并等待 y/N
  -> 用户输入 y
  -> worker 领取任务、执行采集、回调结果
  -> 后端入库并刷新画像/推荐
```

设计边界：

- 默认关闭：`assistant.local-worker.enabled=false`。
- 只允许本机 loopback 地址调用，避免局域网或公网用户触发服务器执行脚本。
- 当前自动打开可见终端实现只面向 Windows，因为用户需要在 PowerShell 窗口中确认授权。
- 前端请求只允许配置 `dryRun` 和 `limit`，不允许传任意命令，也不允许传 `--yes`。
- 后端启动的是本项目固定脚本 `scripts/codex_query_worker.py`，不执行用户自定义命令。
- 线上协作平台不应该开启该能力；线上应让每个用户在自己的电脑运行 Local Agent，再把结果上传到服务端。

配置示例：

```yaml
assistant:
  local-worker:
    enabled: true
    base-url: http://localhost:8080
    script-path: scripts/codex_query_worker.py
    python-command: py -3
    limit: 20
```

测试覆盖：

- `ApiMockMvcTest.localWorkerStartIsDisabledByDefault` 验证默认关闭，避免本地命令启动能力被误开。
- 现有 `codex_query_worker` Python 测试继续覆盖 result callback DTO 契约和敏感信息策略。
## 本地 Agent 与后端任务调度结论

当前项目的正确边界是：后端负责创建任务、接收结果、保存行为、生成画像和推荐；用户电脑上的应用使用情况必须由本机 Local Agent、Codex CLI worker 或 Python 代理在用户显式运行和确认后采集。

不建议让远端 Spring Boot 直接“访问用户电脑”：

- 远端后端只能访问服务器本身，不能直接访问用户个人电脑。
- 进程名、窗口标题、浏览器历史都属于本地敏感信息。
- 小红书、抖音、微信、B站等个人行为数据没有稳定通用开放 API。
- 直接模拟登录、读取 Cookie/Token 或绕过风控不适合作为项目能力。

推荐链路：

```text
前端点击请求采集
  -> Spring Boot 创建 PENDING 任务
  -> 用户本机 PowerShell 运行 worker
  -> worker 展示采集范围并等待确认
  -> worker 调用本地 Python 代理或 Codex CLI
  -> POST /api/v1/behavior-events/batch
  -> Profile / Recommendation 更新
```

本地脚本：

```powershell
py -3 .\scripts\codex_app_proxy.py --user-id alice --dry-run
py -3 .\scripts\codex_app_proxy.py --user-id alice --once --base-url http://localhost:8080
```

## 推荐 12 小时刷新与小红书摘要增强

本轮将推荐刷新策略收敛为“自动 12 小时更新 + 用户手动强制刷新”：

- `GET /api/recommendations/today?userId=me`：页面自动读取今日推荐。如果没有推荐、推荐已过期，或近 24 小时行为发生变化后需要兜底，后端会尝试生成推荐；没有数据时返回 `status=EMPTY`，不返回 500。
- `POST /api/recommendations/refresh?userId=me`：手动强制刷新入口。前端“强制刷新推荐”和顶部“重算推荐”都走这个接口，会删除当天旧推荐并重新生成。
- `GET /api/recommendations/refresh-policy?userId=me`：返回 `refreshHours=12`、`latestRecommendationAt`、`expiresAt`、`expired`、`recentActivityCount`，用于前端展示“推荐什么时候过期”。

这样做的原因是：个人兴趣推荐不需要每几分钟重算；12 小时既能覆盖上午/晚上两次兴趣变化，也能避免频繁重算导致推荐结果抖动。用户主动点击刷新时则明确表达了“现在要新结果”，所以后端直接强制刷新。

```text
  -> POST /api/agent/queries/{taskId}/result 回调后端
```

新增 `GET /api/platforms/xiaohongshu/usage-summary?userId=me`，把小红书信号分成三层：

- `LOW / APP_USAGE_SNAPSHOT`：来自本机可见窗口或应用标题，只能说明“可能正在使用小红书”。
- `MEDIUM / BROWSER_HISTORY`：来自授权导入的浏览器历史 URL，能说明“访问过小红书网页”。
- `HIGH / PAGE_VISIBLE_CONTENT`：来自公开页面 URL、页面可见内容摘要或后续浏览器插件，适合用于更准确的主题推荐。

## Codex CLI 分析模式

`scripts/codex_query_worker.py` 已从“Agent-style 本地 worker”扩展为“两段式 worker”：

```text
采集阶段：
  collect_task / collect_visible_apps / collect_local_notes / collect_bilibili / collect_youtube / collect_xiaohongshu
  -> 只产出授权范围内的非敏感 raw_items

分析阶段：
  可选调用 Codex CLI
  -> 只基于 raw_items 做摘要、分类、标签和置信度补充
  -> 不读取文件系统、不访问外部网络、不推测不存在的访问记录

回调阶段：
  字段白名单过滤 + sanitize + contains_sensitive 二次校验
  -> POST /api/agent/queries/{taskId}/result
```

新增参数：

- `--use-codex-cli`：启用 Codex CLI 分析层。
- `--codex-command`：指定 Codex CLI 命令，默认 `codex`。
- `--print-codex-prompt`：打印发送给 Codex CLI 的 prompt。
- `--print-codex-output`：打印 Codex CLI 原始输出。
- `--codex-timeout`：限制 Codex CLI 分析超时时间，默认 60 秒。

安全约束：

- Codex CLI 不替代采集器，只分析 worker 已经采集到的 `raw_items`。
- Prompt 明确要求不访问文件系统、不调用外部网络、不读取 Cookie、Token、Session、账号密码、聊天记录、私信、支付记录。
- Codex 输出必须是 JSON，格式为 `{ "items": [...] }`。
- Codex 输出如果是 Markdown，会尝试提取 JSON；提取失败则 fallback。
- Codex 输出会再次做字段白名单过滤，只允许 `platform/type/externalId/title/url/author/summary/tags/confidence/dataLevel/detectionReason/matchedKeyword/occurredAt`。
- 发现 `cookie/token/session/password/authorization/私信/聊天记录/支付记录` 等敏感字段或内容时，丢弃 Codex 输出并 fallback 到原始 `raw_items`。

数据置信度规则：

- `visible-window`：`LOW / APP_USAGE_SNAPSHOT`。
- `browser-history`：`MEDIUM / BROWSER_HISTORY`。
- `browser-extension` 或 `page-visit`：`HIGH / PAGE_VISIBLE_CONTENT`。
- 用户提供的公开 URL：`MEDIUM / PUBLIC_URL`。

PowerShell 示例：

```powershell
py -3 .\scripts\codex_query_worker.py --once --base-url http://localhost:8080

py -3 .\scripts\codex_query_worker.py `
  --once `
  --base-url http://localhost:8080 `
  --use-codex-cli `
  --codex-command codex `
  --print-codex-output

py -3 .\scripts\codex_query_worker.py `
  --once `
  --dry-run `
  --base-url http://localhost:8080 `
  --use-codex-cli `
  --print-codex-prompt `
  --print-codex-output
```

本轮新增 Python 单元测试覆盖：

- Codex CLI 不存在时 fallback。
- Codex CLI 返回合法 JSON 时使用 analyzed items。
- Codex CLI 返回非 JSON 时 fallback。
- Codex CLI 输出包含敏感字段时 fallback。
- visible-window 事件默认标记 `LOW`。
- 小红书窗口标题可识别为 `xiaohongshu`。
- Chrome/Edge 不会仅因浏览器进程名被识别为小红书。

## 阶段性产品化重构

本轮围绕“真实访问行为 -> 可信度分级 -> 用户画像 -> 推荐”的链路做了收敛。

### 当前存储方式

默认本地开发仍使用 H2 文件数据库：

```yaml
spring:
  datasource:
    url: jdbc:h2:file:./data/assistantdb;FILE_LOCK=NO
```

MySQL 已通过 `application-mysql.yml` 支持线上或多人场景。`data/imports`、`data/local-notes`、Codex Agent 的 JSON 目录主要承担样例、导入和文件型 Agent 存储；行为、画像、推荐主链路走 JPA 数据库。

### 行为可信度字段

`UserActivity` 新增并贯通以下字段：

- `confidence`
- `dataLevel`
- `source`
- `detectionReason`
- `matchedKeyword`

规则：

- 当前可见窗口快照：`LOW / APP_USAGE_SNAPSHOT`。
- 浏览器历史：`MEDIUM / BROWSER_HISTORY`。
- 页面公开内容：`HIGH / PAGE_VISIBLE_CONTENT`。
- 用户主动输入或公开 URL：`MEDIUM/HIGH / PUBLIC_URL`。

`ActivityService` 会对旧接口自动补默认值。`BehaviorEventService`、`AgentTaskService` 和 worker 回调会保留 Codex CLI 或本地采集器给出的可信度信息。

### 画像过滤规则

`ProfileService.learnFrom` 和每日画像构建会过滤低质量事件：

- LOW + APP_USAGE_SNAPSHOT 不进入长期兴趣词强化；
- 空标题、空摘要数据不作为画像证据；
- 乱码标题不参与画像；
- `WindowsTerminal`、`TextInputHost`、`SystemSettings`、`PowerShell` 等系统窗口不作为兴趣标签；
- 浏览器历史和页面内容优先于窗口标题。

这保证“Visible app: chrome”不会被解释成用户访问了某个小红书笔记。

### 登录和用户隔离

新增轻量 Session 登录：

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`

默认 `assistant.auth.enabled=false`，本地开发继续兼容旧流程。公网或 2-3 人试用时开启后，后端会优先使用 Session 用户，忽略前端传入的 `userId`，从而避免普通用户冒充其他用户查看画像和推荐。

第一版用户来自配置：

```yaml
assistant:
  auth:
    enabled: true
    users:
      - user-id: alice
        password: ${HABIT_ALICE_PASSWORD}
        admin: false
```

### 开发数据清理

新增：

```text
POST /api/admin/dev/reset-data
```

接口行为：

1. 创建 `data/backups/YYYYMMDD_HHmmss/`；
2. 导出 JPA 表数据到 JSON；
3. 移动 `data/processed`、`data/profiles`、`data/recommendations` 等文件型目录到备份；
4. 清空行为、兴趣词、推荐、内容、Agent Query、Codex Agent 画像和推荐数据；
5. 不删除表结构。

本轮没有自动执行 reset，避免误删你当前 MySQL/H2 中的有效测试数据。需要清理时由你手动调用接口。

### 前端布局

前端改为更紧凑的工作台：

- 左侧固定展示当前用户、登录区、关注平台、刷新策略、近 24 小时行为、小红书使用情况、画像关键词；
- 主区域保留本地 worker 调用、应用/网页访问信号、访问网页内容、今日推荐；
- 小红书使用情况展示窗口快照数、浏览器历史数、页面内容数、最高可信度和是否可用于推荐；
- 事件列表展示 `confidence` 和 `dataLevel`；
- 过滤系统窗口，不把系统进程直接展示成兴趣内容。
