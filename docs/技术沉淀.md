# 技术沉淀：本地 Worker、Agent Reach 与 Codex/LLM 兴趣分析

## 设计目标

本项目把个人兴趣数据处理拆成四个清晰边界：

1. 本地 worker：只在用户授权后读取公开 URL、浏览器历史元数据、模拟数据或授权目录内容。
2. Agent Reach/公开元数据工具：读取公开页面或公开视频元数据，输出可解释的公开内容上下文。
3. Codex/LLM：只基于 worker 传入的公开上下文做兴趣理解，不做采集。
4. Spring Boot：接收标准 `behavior_event`，入库、画像学习、推荐生成。

核心原则是：让数据采集留在用户本机控制边界内，让 LLM 只参与“理解公开内容”，而不是接触 Cookie、Token、Session、聊天记录、账号密码或平台私有接口。

## 为什么不让 Spring Boot 直接读取本机数据

Spring Boot 是服务端进程。即使它运行在本机，也不应该直接读取浏览器历史、窗口标题、本地文件或平台数据，因为这会让权限边界变得模糊。

当前设计要求：

- 只有用户显式启动 worker，才会发生本地读取。
- worker 只读取授权范围内的公开 URL、标题、访问时间、访问次数或模拟数据。
- 后端只接收结构化 `behavior_event`。
- 后端错误统一返回 JSON，避免 500 隐藏真实原因。
- 无效事件进入 `INVALID_EVENT_LOG`，但日志不打印敏感原文。

## 为什么 Agent Reach 放在本地 Worker

Agent Reach 或公开元数据工具可能依赖本地 CLI、代理、平台工具或用户手动配置。把它放在 worker，而不是后端，有几个好处：

- 用户能在终端看到即将执行的命令。
- verbose 模式能打印输入、输出、behavior_event JSON 和后端响应。
- 后端不保存平台凭据，也不碰本机私有状态。
- 第一阶段可以用 mock/dry-run 跑通链路，真实读取替换时仍保持相同输出契约。

当前 dry-run 示例：

```text
[AgentReach] 即将执行命令: agent-reach read --url "<url>" --platform "<platform>" --dry-run
[AgentReach] 返回结果: {...}
```

## Codex/LLM 的作用

LLM 是兴趣理解层，不是采集层。它的输入来自 worker 已经拿到的公开上下文。

对于 YouTube，当前输入结构是：

```json
{
  "title": "Spring Boot Redis caching tutorial",
  "description": "A public description from YouTube metadata.",
  "author": "Backend Channel",
  "url": "https://www.youtube.com/watch?v=yt123456",
  "videoId": "yt123456"
}
```

LLM 输出严格 JSON：

```json
{
  "summary": "This video explains Spring Boot Redis caching for backend APIs.",
  "tags": ["spring boot", "redis", "backend"],
  "interestCategory": "backend",
  "confidence": "HIGH"
}
```

这一步的收益：

- 把“看过一个 URL”升级为“看过一个关于后端缓存优化的视频”。
- 去掉系统标签，只保留内容标签。
- 生成短摘要，让画像和推荐更可解释。
- 用 `interestCategory` 降低后续推荐召回的噪声。
- 用 `confidence` 帮助画像服务区分证据强弱。

## 实时 LLM 分析

worker 在 ingestion 前会为每个满足条件的访问 URL 事件提交异步 LLM 分析任务。当前触发条件已经收敛为：

- `url` 非空
- `eventType` 是 `VISIT`、`WATCH` 或 `FAVORITE`

`APP_USAGE`、无 URL 的 `SEARCH`、纯窗口标题和本地 App 快照不会进入 LLM。这一层筛选放在 analyzer 前，目的是让 LLM 只理解“用户访问了某个公开内容”这类事件，而不是把本地使用状态误判成内容兴趣。

输入结构：

```json
{
  "platform": "youtube",
  "url": "https://www.youtube.com/watch?v=yt123456",
  "title": "Spring Boot Redis caching tutorial",
  "contentSnippet": "Public content summary",
  "eventType": "WATCH"
}
```

prompt 要求 Codex/LLM 输出严格 JSON：

```json
{
  "summary": "...",
  "tags": ["..."],
  "interestCategory": "...",
  "intent": "...",
  "confidence": "HIGH"
}
```

LLM 调用使用线程池异步执行。主 ingestion 流程继续向后端写入事件，不等待单个 LLM 请求完成。分析完成后，CLI 立即打印：

```text
=====================================
[LLM ANALYSIS RESULT]
Platform: xxx
URL: xxx
Summary: xxx
Tags: xxx
Category: xxx
Confidence: xxx
=====================================
```

同时打印结构化日志：

- `llm_input_log`
- `llm_output_log`
- `latency_ms`
- `token_usage`，如果模型或 CLI 返回该字段

如果 LLM 不可用或分析失败，事件仍然入库；metadata 会标记 `llm_status=FAILED`，并记录脱敏后的错误原因。

安全约束：

- 不允许读取文件系统。
- 不允许读取 Cookie、Token、Session、账号密码、聊天记录、私信、支付记录。
- 不允许调用外部网络补数据。
- 如果原始数据没有 URL，不允许编造 URL。
- 输出必须是严格 JSON。
- 如果输出包含敏感字段或敏感推断，worker 拒绝并回退。

## LLM Gateway 设计

这次把 LLM 执行从 worker 主流程里抽成了统一网关：

```text
codex_query_worker.py
  -> WorkerLLMGateway
  -> CodexAnalyzer
  -> LLMGateway
  -> Codex CLI / LLM command
```

职责划分：

- `codex_query_worker.py` 只负责采集、enrichment、生成 behavior_event 和 POST。
- `WorkerLLMGateway` 是 worker 侧唯一入口，避免业务流程直接依赖 analyzer 内部细节。
- `CodexAnalyzer` 负责事件筛选、异步线程池、prompt 构建、结果校验、CLI 实时输出。
- `LLMGateway` 负责命令解析、子进程执行、严格 JSON 解析、`latency_ms/token_usage` 记录和错误脱敏。

这样拆的收益：

- WinError、命令解析、JSON 解析这类执行层问题集中在一个文件里修。
- analyzer 可以专注“哪些事件该分析、分析结果如何回填”。
- worker 后续替换成其他 LLM 命令或 mock 时，只需要替换 Gateway 层。
- 测试可以分别覆盖事件筛选、Gateway 命令解析、真实字段回填和 CLI 打印。

### WinError 2 排查记录

Windows 上通过 npm/pipx 安装的 Codex CLI 可能解析为 `codex.cmd`。如果直接把 `["codex", ...]` 交给 `subprocess.run()`，在某些环境下会出现 `WinError 2` 或找不到可执行文件。

修复策略：

- `LLMGateway.resolve_command()` 使用 `shutil.which()` 在 worker 的 `tool_env()` PATH 中解析真实命令。
- 如果解析结果是 `.cmd` 或 `.bat`，使用 `subprocess.list2cmdline()` 拼成命令字符串，并通过 `shell=True` 执行。
- 旧的 `run_codex_cli()` 兼容路径也改为复用 `LLMGateway.resolve_command()`，避免遗留路径再次触发 WinError。

### LLM 输出回填策略

LLM 成功后不能只把结果放进 `rawMetadata.llm_result`，否则后续 ingestion/profile 仍然看到旧的 placeholder 字段。当前回填规则是：

- 顶层 `summary` 覆盖为 LLM 摘要。
- 顶层 `tags` 覆盖为内容语义标签，过滤 `youtube`、`agent-reach`、`public-url` 等系统标签。
- 顶层 `interestCategory`、`intent`、`confidence` 使用 LLM 返回值。
- `summaryForProfile`、`contentCategory` 与顶层语义字段保持一致。
- `rawMetadata.llm_status=SUCCESS`，并记录 `llm_result` 与 `llm_latency_ms`。

## Worker 完整处理链路

```text
Spring Boot 创建任务
  -> worker 领取任务
  -> 用户确认授权
  -> worker 读取授权 URL 或 browser_history_sample.json
  -> 平台识别和 URL 归一化
  -> Agent Reach/yt-dlp 读取公开元数据
  -> YouTube context: title, description, author, url, videoId
  -> 异步 Codex/LLM 生成 summary/tags/interestCategory/intent/confidence
  -> CLI 实时打印 [LLM ANALYSIS RESULT]
  -> worker 覆盖 placeholder tags
  -> 生成标准 behavior_event JSON
  -> POST /api/v1/behavior-events/batch
  -> 后端 adapter 归一化
  -> BehaviorEventValidator 入库前校验
  -> ActivityService 保存 UserActivity
  -> ProfileService / RecommendationService 更新画像和推荐
```

调试命令：

```powershell
py -3 scripts/codex_query_worker.py --once --yes --use-codex-cli --direct-behavior-batch --verbose
```

verbose 会打印：

- 当前任务
- 采集到的 raw items
- Agent Reach 命令和输出
- Codex CLI 命令、输入和输出
- behavior_event JSON
- 后端 POST URL 和响应

## 多平台归一化

后端 adapter 层把平台差异收敛为统一结构：

```json
{
  "userId": "me",
  "platform": "youtube | bilibili | baidu | xiaohongshu | web",
  "eventType": "VISIT | WATCH | SEARCH | FAVORITE",
  "url": "https://...",
  "externalId": "...",
  "title": "...",
  "author": "...",
  "contentSnippet": "...",
  "occurredAt": "2026-06-12T10:00:00",
  "rawMetadata": {}
}
```

adapter 职责：

- `YouTubeAdapter`：提取 videoId，重建 `https://www.youtube.com/watch?v=...`。
- `BilibiliAdapter`：提取 BV/av id，重建 canonical video URL。
- `BaiduSearchAdapter`：把搜索词保存到 `rawMetadata.query`。
- `XiaohongshuAdapter`：提取 noteId，重建 canonical note URL。
- `GenericWebAdapter`：归一化普通网页 URL，移除 tracking 参数。

## 入库前校验

`BehaviorEventValidator` 是全局校验层，拒绝：

- unknown platform
- `url` 和 `externalId` 都为空
- `eventType` 缺失
- platform/url mismatch，例如 `platform=youtube` 但 URL 是 Bilibili

拒绝事件会写入 `INVALID_EVENT_LOG`。日志只记录 reason、userId、platform、eventType、urlHost、externalIdPresent，不记录 Cookie、Token、Session 或长文本原文。

## 500 问题排查过程

曾经的 500 风险主要来自：

1. JSON 字段不匹配：worker 发 `eventType`，后端只认 `type`。
2. 时间格式不匹配：客户端发带时区 ISO-8601，DTO 使用 `LocalDateTime` 直接解析失败。
3. 对象/数组字段不匹配：`tags`、`rawEvidence` 没有统一处理。
4. 字段长度不足：长 `text` 或 JSON metadata 写库失败。
5. 平台字段散落在 service 中，新增平台容易漏校验。

修复结果：

- DTO 支持 `eventType`、`createdAt`、`interestCategory`、`rawMetadata` 别名。
- `occurredAt` 支持本地或带时区 ISO-8601。
- `tags` 使用 `List<String>`。
- `rawEvidence/rawMetadata` 经过白名单和长度限制后保存为 JSON 文本。
- 新增 adapter 层和 validator 层。
- 全局异常响应包含 `success=false`、`message`、`path`。
- MockMvc 覆盖标准 behavior_event、多平台归一化和非法事件拒绝。

## 项目结构分析

```text
src/main/java/com/example/assistant
  controller/              API 入口，保持薄控制器
  dto/                     外部输入输出契约
  model/                   持久化实体和枚举
  repo/                    数据访问
  service/                 画像、推荐、采集、调度等业务逻辑
  service/behavior/        behavior_event 入库主链路
  service/behavior/adapter 平台归一化扩展点
  service/agent/           agent task/query 生命周期
  codexagent/              Codex Data Agent 模块

scripts/
  codex_query_worker.py    本地 worker 主流程
  agent_reach_adapter.py   Agent Reach mock/dry-run 适配
  worker_llm_gateway.py    worker 侧统一 LLM 入口
  llm_gateway.py           Codex/LLM 子进程执行、JSON 解析和 WinError 2 兼容层
  codex_analyzer.py        异步 LLM 分析、事件筛选和 CLI 实时输出
  test_*.py                worker 策略和契约测试
```

结构优点：

- 后端不直接读本机数据。
- worker 不直接访问数据库，只通过 HTTP 回传结构化事件。
- 平台归一化通过 adapter 扩展，不再堆在 service 中。
- LLM 分析在本地 worker 内完成，失败可回退。

当前基础优化：

- `BehaviorEventService` 已改为每条事件只 normalize/validate 一次，Activity 入库和消息发布复用同一个 `UnifiedBehaviorEvent`。
- `ActivityService` 的 rawEvidence 白名单增加了统一 schema 字段。
- worker 的 YouTube tags 在 LLM 分析后强制覆盖 placeholder/system tags。
- worker 的实时 LLM 分析已统一经过 `WorkerLLMGateway -> CodexAnalyzer -> LLMGateway`，避免执行层逻辑散落在主流程里。

后续优化方向：

- 将 `codex_query_worker.py` 拆成 `collectors/`、`analysis/`、`policy/`、`transport/`。
- 将 Codex prompt 提取为模板文件，便于版本化。
- 为 `rawMetadata` 增加 schema version。
- 将 Agent Reach mock 替换为真实读取时保持 dry-run、verbose 和同一输出结构。
- 增加端到端测试：创建任务 -> worker dry-run -> direct behavior batch -> profile/recommendation。
